# UI/UX現状調査と再編案 — 2026-09-20

## 調査結果

現状の主な問題は、日常操作の途中に実装上の区分や技術情報が入り、利用者が次の操作を判断しにくいことにある。登録の段階数、主要画面への入口の重複、取得・検証フローの情報量を先に整理する。配色や角丸だけを変更しても、これらの問題は解消しない。

今回の対象は、ユーザーが挙げた4点の修正と、全体再編に向けた調査まで。全体再編は以下のProposalであり、実装済みの仕様ではない。

- **Fact**: コードとリソースから確認した動作・構造。
- **Assessment**: その構造が利用者に与える負担についての評価。操作観察による実証とは区別する。
- **Proposal**: 次回の再編候補。
- **NOT_RUN**: 実機や描画で未確認の事項。

基点はローカル`develop`の`dedab20`。リモートには`develop`が存在せず、リモートの同名ブランチとの同期は確認できていない。今回の実装を含め、対象はAndroidリポジトリのみ。

## 今回修正した4点

| 項目 | 修正前のFact | 修正後の動作 |
| --- | --- | --- |
| 登録URL | GitHub/Codebergともパスが厳密に2階層でなければ拒否。クエリ・フラグメントも拒否 | owner/repositoryを抽出。`/release`、`/releases/tag/v1`、IssueやツリーのURL、クエリ・フラグメント付きURLを受け付ける |
| APKが1件 | リリース候補を取得フローへ渡す経路では未選択。画面には1件でもラジオボタンと「複数ある」説明が出る | 唯一のAPKを画面で自動選択し、ラジオボタンを省く。「公式APKをダウンロード」を押すと従来の選択・取得処理へ進む |
| 今後のリリースへの確認 | APK選択画面に同名ファイルを将来も使用するかのチェックボックスがある | チェック項目を削除。画面から新しい保存条件を追加せず、既存の保存条件のデータと解除操作は維持する |
| 同バージョンの更新表示 | 詳細画面はAPKの`UP_TO_DATE`より候補の存在を優先して更新操作を出す | 同じアプリ・リリースID・観測ハッシュに属するAPKが最新または導入済みより古ければ候補を更新操作から除外。登録完了画面にも適用。詳細画面への進入・復帰時に既存のインストール状態再確認処理を呼ぶ |

URLの抽出は登録対象の入力に適用する。HTTPS、正規の配布元ホスト、ユーザー情報・ポートの禁止、owner/repositoryの文字検証、入力長上限は維持する。APKダウンロードURLの検証は従来のまま。

自動選択は取得画面の初期選択であり、選択だけでは通信を開始しない。ダウンロードはボタン操作で開始する。Roomのスキーマ変更や既存データの一括書換えはない。

バージョン判定はAPKの`versionCode`による既存の比較を使う。表示名やタグ名が同じという理由だけでは、同一APKとは判定しない。同じタグで観測内容が変わったリリースや、未検査の候補は一律に非表示にしない。

## 推奨する画面構成 — Proposal

```text
アプリ一覧
  ├─ 追加 → URL入力 → アプリ確認・登録 → 必要なら取得へ
  ├─ アプリ詳細
  │    ├─ 主操作：取得／更新／リリース内容の確認
  │    ├─ 検証：未実施・実行中・結果 → 検証開始／結果を見る
  │    ├─ 設定
  │    └─ 技術情報・履歴
  └─ 全体設定
       ├─ 表示・通知
       ├─ 更新確認
       ├─ 取得・インストール
       ├─ 検証環境・Runner
       └─ データ管理・アプリ情報
```

| 画面 | 最初に見せる内容 | 主操作 | 詳細へ回す内容 |
| --- | --- | --- | --- |
| 一覧 | アイコン、アプリ名、導入版、対応が必要な状態 | アプリを開く。画面全体の追加はFAB | リポジトリ文字列、検証証拠 |
| 登録 | URL、解決したアプリ・提供元、登録目的 | 登録する | リポジトリID、コミット、探索状態、個別のビルド設定 |
| アプリ詳細 | 導入版と候補、確認日時、検証状態 | 状態に応じた操作を1つ強調 | ハッシュ、署名の詳細、履歴、低頻度設定 |
| APK取得 | ファイル名・サイズ、選択状態、取得進捗 | ダウンロード。取得後は条件を満たす場合にインストール | MIME、配布元時刻、digestなどのメタデータ |
| 検証 | 現在の工程、進捗、結果、失敗時の次の操作 | 開始、必要な確認、結果表示のいずれか | 生ログ、Job内部値、各比較軸の証拠 |

未検査のリリース情報だけでは「更新あり」を断定せず、導入可否を確認できる操作として表現する。主操作の優先順位は「同版」「旧版」「未導入」「新版」「未検査」「検証中」の具体的な状態ごとに決める。

確認の削減は、選択肢が1つしかない操作、入力内容の繰り返し確認、操作を伴わない状態表示から進める。インストールや署名不一致、外部コード実行など、判断内容が変わる操作では必要な情報をその場に置く。

## 再編の着手順 — Proposal

1. 登録→APK取得→アプリ詳細の通常利用を一本のフローとして整理する。各状態の文言と主操作を先に確定する。
2. この3画面のコンパクト端末向けレイアウトを作り、長いアプリ名・APK名、日本語、大きな文字でも操作が成立することを確認する。
3. 設定、Runner、検証結果、技術詳細の階層を整理する。
4. 共通の余白、見出し、面色、状態表示をまとめ、light/dark/dynamic colorで確認する。
5. 横長・大画面では一覧と詳細の併置などを検討する。現在の縦画面を横に引き伸ばすだけの構成にはしない。
